# Cron recipient UI proof

This task-only branch belongs on `steipete/openclaw:codex/cron-recipient-ui-proof`. It runs one fixed before/after comparison for [OpenClaw #134368](https://github.com/openclaw/openclaw/pull/134368), not an upstream workflow or default-branch change. A push triggers the fixed job; the manual trigger accepts no arbitrary source or command. Execution remains pending until the reviewed packet is published.

The baseline is trusted main `af531525c46444521986002d64b888ee5ed097cb` (tree `117f79bc03b11cb436872695bac6210bb0127a57`). Both stages receive the identical four-case E2E fixture and one canonical private-source-server classification entry. Only after the baseline exhibits all three intended suggestion failures and passes the valid-recipient manual-entry control does the driver write the reviewed replacement for `ui/src/pages/cron/form-suggestions.ts`. That owner-only repair is +3/−7 production lines. Its SHA-256 is `4e1b18dcd4dcc841ab1285990bcd25b8d817d67ada8100e8ad01f951770d86c5`; it is an independently authored data overlay, not a published PR commit. The final landed candidate must be rebound to these exact owner and seam bytes.

The real application boots through the existing source-Vite server and mock Gateway WebSocket. Raw `channels.status` and `cron.list` responses feed the actual CronPage and suggestion owner; no prepared suggestions or application state are injected. The tests inspect separate Recipient and Account ID datalists for Telegram, `last`, and webhook modes. They preserve a valid numeric Telegram recipient whose spelling equals a same-channel account display name, type the complete value through the real input, and check its separate `delivery.to` and `delivery.accountId` in the actual `cron.update` request. The cron scheduler, real delivery services, provider inference, and persistence are outside this UI projection proof; no `cron.run` call is allowed.

Every case retains its own synthetic screenshot, closed-context video, raw RPC fixtures, request log, DOM options, and served-owner response hash. The collision case proves datalist membership and manual keyboard entry/save; its recorded input method is `manual-keyboard-text`. It does not claim native popup selection. No popup is recreated or injected for a picture. After download, the complete pictures/videos still need inspection before attachment to the PR.

The workflow uses ephemeral GitHub-hosted Ubuntu 24.04, pinned actions, read-only repository contents, no repository secrets, no environment or cloud role, and no persisted checkout credentials. Node 24.19.0 and the exact repository `pnpm@12.1.0+sha512...` pin are verified. An ordinary fresh frozen installation and the existing Chromium/ffmpeg setup owner prepare the runner. The standard `scripts/run-vitest.mjs` command uses the canonical UI E2E config; there is no full-build bypass, custom test config, shortened assertion, increased test timeout, live account, or credential hydration. Child processes receive a small explicit environment and fresh per-stage HOME/XDG/state defaults, with a shared public browser/toolchain cache. This is ordinary hosted isolation, not a network firewall.

All 48 selected baseline source/dependency inputs are hash-bound, and every tracked file, the commit/tree, and raw index are snapshotted and compared around installation and both UI stages. The installed lock and test bytes stay fixed; the driver permits only the documented classification entry and then the one owner overlay. Source files, dependency pins, and Git index are not edited by tests. Both success and failure retain command logs, JSON reports, source snapshots, media, and artifact hashes. No candidate output is printed directly into Actions commands. The driver closes and kills its tracked command process group on outer timeout, the existing suite owns browser/server cleanup, and the ephemeral runner bounds remaining scratch state.

Its root cause is unproven; neither headless limitations nor a form rerender bug are established. The fourth case is explicitly renamed to manual entry and retains the same exact target/account/save assertions. Telegram, `last`, and webhook contamination assertions are unchanged. The webhook wait uses the actual associated label and required state, because the former exact text locator missed the label's required marker. The earlier failed evidence remains intact.
